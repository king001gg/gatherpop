# 围响 GatherPop

[![test](https://github.com/king001gg/gatherpop/actions/workflows/test.yml/badge.svg)](https://github.com/king001gg/gatherpop/actions/workflows/test.yml)
[![license: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
[![zero dependencies](https://img.shields.io/badge/dependencies-0-brightgreen.svg)](#跑起来)

聚会场景下的轻量游戏工具箱。定位不是「游戏平台」，而是**一群人聚在一起、不知道玩什么的时候，第一个想到的工具**。

所以第一优先级不是游戏数量，而是：打开快、不用登录、没有广告打断、方案可自定义、联机不依赖外网。

---

## 跑起来

**没有编译步骤，也没有工具链要装。** 交付物就是 `index.html` 一个文件，用浏览器打开就能玩。

```
# 只是想玩：双击 index.html，或者把它丢给任何人
# 也可以直接开线上那份（就是同一个文件）：https://king001gg.github.io/gatherpop/

# 想改代码，跑测试（需要 Node 20+）
npm install     # 只有二维码测试要用；游戏本身零依赖
npm test        # 300 个测试

# 想两台设备联机（真机测试用）
node serve.mjs  # 起一个局域网静态服务器，会把该用的地址打印出来
```

> **联机优先用 `serve.mjs` 起的局域网地址，别用线上那份。** 邀请链接是按
> `location.origin` 生成的 —— 从公网页面建房，码里写的就是公网地址，两台设备
> 都从公网取页面再点对点连。信令仍然只走二维码（片段不会被发往服务器），
> 但「从公网页面访问局域网设备」正是 Chrome LNA 管的场景，可能被拦。
> 线上那份用来**单机玩**和**分享给朋友**最合适。

> `npm install` 装的两个包（`qrcode`、`jsqr`）**只当测试对照**用 —— 一个是逐模块比对的
> 参考实现，一个反向验证渲染出的像素真能被扫码器读出来。它们不进 `index.html`，
> 交付物永远是零依赖的。跳过这一步的话，`test/qr.test.mjs` 会在装载时直接报错。

## 现在能跑什么

- 首页按**聚会节奏**分组（等人暖场 / 饭前饭后 / 想认真玩 / 两人打发时间 / 记分随机），而不是按游戏类型罗列
- 房间是核心：成员栏、游戏切换栏、**常驻记分牌**、今晚玩过哪些局
- 十款游戏：**骰子**、**转盘**、**谁是卧底**、**抽卡**、**记分牌**、**五子棋**、**国际象棋**、**象棋**、**狼人杀**、**你画我猜**
- **方案市场**（没有服务器）：官方种子方案 + 自己另存的 + 一条 `GP1` 分享码互相换
- **扫码联机**：房主点「邀请玩家」出一张码，朋友用相机扫一下就进来。点对点直连，没有服务器中转

---

## 四条不可动摇的规则

1. **记分牌属于房间，不属于游戏。** 这是「跨游戏常驻」的唯一实现方式——换游戏时房间状态原封不动，只换挂载的插件。
2. **游戏状态是房主权威的纯函数。** `reduce(state, action)` 不碰 IO，连随机数都从 state 里的 seed 推进。同样的输入必然同样的输出——可测试、可回放。
3. **客户端永远拿不到完整 `GameState`，只拿得到裁剪后的 `GameView`。** 谁是卧底的词靠 `viewFor` 挡住。这不是靠自觉，是类型/接口层面的硬约束：`render(view, ctx)` 的签名里根本没有 `state`。
4. **`RoomController` 不知道传输方式。** 单机、局域网、WebRTC 走同一套房间逻辑，区别只在注入哪个 transport。

## 扫码配对怎么走通的

一次往返，两个码：

```
房主                          加入端
 │  ① 亮出邀请码（#o=…）
 ├──────────────────────────►  用系统相机扫 → 打开页面
 │                              ② 生成回执码（#a=…）
 │  ◄──────────────────────────
 │  用系统相机扫回执
 │      ↓
 │  打开一个**新标签页**，它把回执通过 BroadcastChannel 转回原页面
 │      ↓
 └─ 原页面里那个发出 offer 的 RTCPeerConnection 原地存活 → 握手完成
```

三个刻意的取舍：

- **不做 trickle ICE。** 等候选收集完再一把塞进二维码，换「每个方向只要一个码」。代价是收集期间多等一两秒。
- **全程不调用 `getUserMedia`。** 扫码用手机系统相机，系统相机不受页面安全上下文限制 —— 所以**这个页面不需要任何相机权限**，也就没有 HTTPS 硬要求。
- **回执必须转送回原标签页。** 新标签页自己完不成握手（发出 offer 的 `RTCPeerConnection` 在原来那页），所以同源的 `BroadcastChannel` 是这套流程的关键。这也顺带**完全免掉了 JS 二维码解码器**——系统相机就是解码器。

转送不是「发出去就算数」：转送页会等原页面回一声 ack，等不到就明说**没送到**，而不是谎报成功。两个坑值得记一笔：

- `BroadcastChannel` **同页之间的多个通道也会互投**。转送页如果把「听回执」的监听也挂上，它会把自己刚发的回执收回来再自己 ack 自己 —— 于是原页面早就关了，转送页还报成功。所以转送页不挂这个监听。
- 所以「原页面还活着」这件事**是靠 ack 证实的**，不是靠 `postMessage` 没抛异常。

信令全部放在 URL 的 `#` 片段里。**片段永远不会被浏览器发往服务器**，所以哪怕页面托管在公网，信令数据也只在两台设备之间流转。

## 真机怎么测

**先把它托管起来。** 双击打开只够单机玩 —— 两台设备要联机就必须**同源**，同一个 `file://` 在两台机器上算两个来源，`BroadcastChannel` 和 `location.origin` 都对不上：

```
node serve.mjs          # 打印出局域网地址，两台设备开同一个
```

不需要 HTTPS：这个页面全程不调用 `getUserMedia`（扫码用的是手机系统相机），WebRTC 数据通道本身也不要求安全上下文。

> **必须用局域网地址打开，不能用 `localhost`。** 邀请链接是按 `location.origin` 生成的，用 `localhost` 打开的页面生成出来的码里写的就是 `localhost` —— 另一台设备扫了会指向它自己。

联机失败有三类**完全不同**的原因，修法也完全不同。所以配对流程做了两条独立的路，并把诊断摆到台面上：

**第一步：两边都点首页的「联机自检」。**

它真的建一条连接、真的收一遍候选，报的不是「浏览器声称支持」，是「实际拿到了什么」。重点看三行：

| 看到什么 | 意味着 | 该修哪 |
|---|---|---|
| 二维码 `v20` 以上 | 码偏密，扫不动很正常 | 走下面的粘贴路，或者想办法瘦身 SDP |
| **主机候选 0 个** | 这个网络不让设备互相看见 | 换网络（手机热点常常可以）；软件怎么改都没用 |
| 有 mDNS 假名候选 | 要靠组播解析成真 IP | 组播被禁的网络（企业网、部分路由器）会卡死在这 |

**第二步：先走一遍不扫码的路。** 这一遍只验「配得对不对」，把二维码完全排除在外：

1. 房主建房 → 「邀请玩家」→ 出码。**这个浮层里有「扫不了？手动粘回执」，二维码下面也有整条链接。**
2. 把邀请链接用微信/隔空投送给另一台设备，那边打开首页 → **「有邀请码，粘进来」**。
3. 那边出一张回执码，同样把链接发回来 → 房主这边点 **「扫不了？手动粘回执」**。
4. 两边应当各自进房间，房主那边显示「2 人」，另一边显示「已连上房主」。

**这一步通了、扫码那步不通 = 纯粹是二维码太密**，跟 WebRTC 一点关系都没有。反过来，粘链接这条路也连不上，那就是候选/组播/客户端隔离的问题，去查自检里那两行。

**第三步：才开始扫真码。** 前面都通了再看相机这条路顺不顺。

> 加入端以前只能靠扫，码扫不动整个流程就断在那儿，人会分不清是码的问题还是网络的问题 —— 上面那条「粘进来」就是补这个洞的。

**第四步：故意让人掉一次线。** 进房间开一局，把其中一台设备的 Wi-Fi 关掉或锁屏，
房主那边应当看到成员栏里那位变暗；如果正好轮到他，房主点「有人不在了？」，
浮层里会写明跳过后这一局变成什么样，点「跳过」就该能继续玩下去。
**这一步顺便验了掉线检测**：真机上 `dc.onclose` / `connectionstatechange` 到底多久才来。

**第五步：让房主刷新一次。** 开着房间（最好开着一局）按刷新，页面应当**直接落回
房间**，记分牌、历史、这一局都还在，顶上挂着「房间接回来了」——同时其余每个人的
名字都变暗，因为连接确实断了。然后房主重新出码，其他人扫回来：**各自应当拿回原来
的名字和分数**，而不是变成一排新的自己。这一步才算真的验了「认座」。

## 结构

```
index.html              ← 全部代码，零依赖（4964 行）
  CORE:BEGIN/END        ← 核心域：房间语义、游戏插件、信令打包。刻意不依赖 DOM
  QR:BEGIN/END          ← 二维码编码器：手写 Reed-Solomon + 掩码评分
  NET:BEGIN/END         ← WebRtcTransport（要靠 RTCPeerConnection，所以不在 CORE 里）
  gatherpop-ui          ← 界面层
test/core.test.mjs      ← 房间语义、隐藏信息、纯函数性
test/ui.test.mjs        ← 假 DOM 跑真实交互路径 + 配对页面切换
test/net.test.mjs       ← 协议层：假传输把消息**真的 JSON 序列化一遍**，泄露断言才作数
test/pair.test.mjs      ← 传输层：假 RTCPeerConnection 真的把 SDP 传一遍
test/qr.test.mjs        ← 二维码与 qrcode/jsQR 逐模块比对
test/fake-rtc.mjs       ← 共享的假 RTCPeerConnection
audit/mutation.mjs      ← 变异测试：往代码里注入人工缺陷，看测试抓不抓得住
audit/probe.mjs         ← 对抗性探针：畸形报文、恶意名字、越权、泄密矩阵
audit/verify.mjs        ← 对存活的变异逐条取证，分辨真盲区与等价变异
serve.mjs               ← 真机联机测试用的静态服务器，零依赖
.github/workflows/
  test.yml              ← CI：在 Node 20/22/24 上各跑一遍测试
  pages.yml             ← 部署到 GitHub Pages（先过测试再发，站点里只有 index.html）
  mutation.yml          ← 变异测试，手动触发（跑 22 遍全量测试，不适合挂在 push 上）
```

核心块不依赖 DOM，所以能直接在 Node 里测。游戏插件的 `render` 返回 HTML 字符串而不是操作 DOM，交互统一走 `data-act` 属性由外壳代理——这既让插件保持纯粹，也让它们可测。只有你画我猜的 `afterRender` 会碰 DOM，那是画布逼出来的唯一一道口子。

### 测试跑得动，还得测得准

`npm test` 绿只说明代码被执行过，不说明断言真的在把关。所以 `audit/` 下另有三件工具：

- **`audit/mutation.mjs` —— 变异测试。** 往 `index.html` 里注入人工缺陷（把
  `viewFor` 的过滤去掉、把 token 塞进广播快照、把 `esc` 的尖括号转义删掉、把
  seed 推进删掉……），再看测试抓不抓得住。抓住叫杀死，全绿叫存活 ——
  **存活的每一条都是测试的盲区**。当前 22 条全部杀死。
- **`audit/probe.mjs` —— 对抗性探针。** 畸形报文、恶意成员名、越权动作、
  十个插件的泄密矩阵、持久化的垃圾输入，一次跑完只报问题。
- **`audit/verify.mjs` —— 给存活的变异逐条取证。** 存活不一定是洞，也可能是
  语义等价的假变异；这个脚本真的走一遍那条变异代码，看危害能不能复现出来。

上一轮审计靠它挖出并修掉了：对端发一句字面量 `null` 就能让房主的消息处理抛
`TypeError`（入站报文没挡非对象）、`{"t":"action","action":null}` 同理；
另有四处测试盲区（连开两局的洗牌、`esc()` 的尖括号、双预言家的验人结果隔离、
狼人杀 `kill` 的目标合法性），现在都有回归测试守着。

### 加一款新游戏

在 `GAME_PLUGINS` 里加一个实现以下契约的对象即可，核心代码一行都不用改：

```js
{
  id, name, icon, rhythm, minPlayers, maxPlayers,
  createInitialState({ members, preset, seed }),  // → state
  reduce(state, action),                          // → state，纯函数
  canApply(state, actorId, action),               // → boolean，拦越权
  viewFor(state, viewerId),                       // → view ★ 隐藏信息在这里挡住
  render(view, ctx),                              // → HTML 字符串
  summarize(state),                               // 可选：历史里那一行摘要
  skip(state, missingId),                         // 可选：轮到某人但他不在时怎么往下走
  presets / readPreset / presetToText / presetHint, // 可选：方案市场
  uiKeep,                                         // 可选：ctx.ui 里哪些键要留着
  afterRender(view, ctx, root),                   // 可选：唯一允许碰 DOM 的钩子
}
```

`render` 拿到的 `ctx` 里还有两样可选的东西：`ctx.scores`（房间记分牌）和
`ctx.ui`（**本端界面自己的临时状态**，比如象棋选中了哪个格子）。`ctx.ui` 是刻意的
设计：选中的格子既不该进 `state`（那会走网络、进 reduce），也不该进 `view`
（那是房主裁给你看的东西）。它只活在这一台设备的这一屏上，换游戏就清掉。
`uiKeep` 点名的键例外 —— 比如画笔的颜色，画完一笔不该自己弹回去。

### `afterRender` 是为画布开的唯一一道口子

九款游戏都能只用「返回一段 HTML 字符串」表达，**你画我猜不行** —— 画布得等节点
真的挂上去，才能往上画、才能接指针事件。所以契约多了个可选钩子：

```js
afterRender(view, ctx, root)   // root 是本端已经挂好的容器，ctx 里多一个 submit(action)
```

规矩只有两条：**只有它碰 DOM，而且只碰自己那一块**；拿不到节点就安静退出，
无头环境里不许抛。核心域其余部分照旧零 DOM 依赖，`npm test` 里也不需要真浏览器。

画面本身走的是「抬笔才提交」：手指动的时候那一笔只活在本端（存在 `ctx.ui` 里），
抬笔才把整条线当成**一个动作**发出去。规则层因此完全不用知道「手指正在动」，
也不会每挪一下就往网络上扔一条消息。

外壳另外提供了两个通用机制，做「要输入」的游戏时用得上：`<input data-ui="键">`
的内容会镜像进 `ctx.ui.键`（别人动一下触发重渲染时，你正在打的字不会被抹掉）；
动作里写 `"textFrom":"<元素 id>"` 就能把那个框里的内容作为 `action.text` 捎上，
而元素 id 本身不会跟着动作过线。两者都通用，外壳不知道「猜词」这回事。

### `skip`：有人锁屏走开了怎么办

聚会里一定有人手机没电、走开、掉出去。凡是**绑在某个特定成员身上**的阶段
（该他画、该他落子、该他表态），那个人不发动作就永远等不到 —— 这一局就变成
打不完，唯一解是整个丢掉。

插件用 `skip(state, missingId)` 声明「他不在时这局该怎么走」。返回新 state 就是
替他走了这一步，返回 `null` 就是**他现在没卡住任何东西**（界面据此把按钮置灰，
而不是假装跳成功）。规矩只有一条：**尽量委托回自己的 `reduce`**，别把阶段推进
逻辑抄第二遍。棋类替不了 —— 替他落子等于凭空捏造一步棋，所以那一格是判退。

真正做裁决的是房间，不是插件：`{t:'skipPlayer', id}` 在 `RoomController` 里于
插件路径**之前**分流，**只有房主能过**。加入端提交的动作是以它自己的 id 裁决的，
所以它发这个会被直接挡回来，不需要额外加一层校验。

房主侧的入口是房间页的「有人不在了？」。浮层里每个成员旁边**先把结果写出来**
再让人按 —— 对每个成员调一次插件的 `skip`（纯函数，不碰真状态），把算出来的
下一帧交给插件自己的 `summarize` 念成人话，跟历史记录里那一行是同一套说法。
跳过一次不可撤销，值得先把话说清楚。

掉线本身也看得见了：`WebRtcTransport` 在数据通道关掉、或连接转成
`failed`/`closed` 时报一次「这个对端没了」，房间层据此把成员标成不在线。
**传输层只报这个事实**，它不知道「成员」「跳过」这些词（规则 4 不变）。

### 刷新之后：房间还认得回来

误触刷新、手机把标签页回收 —— 一桌人正等着，丢的是成员、常驻记分牌、「今晚玩过
哪些局」，还有打到一半的那一局（狼人杀的第二夜、你画我猜画了一半）。

房主这一侧的房间存进 `localStorage`，重新打开页面**直接落回房间**，12 小时后自动
过期（一次聚会不可能超过 12 小时，第二天打开就是个干净的新房间）。写盘是节流的 ——
你画我猜每抬一次笔就是一帧新状态，而它的笔画最坏能到几百 KB，每个动作都同步序列化
一遍会把画笔卡死；真正保底的是 `pagehide` 和切后台时那一次同步写入。

**但连接是真的断了，大家得重新扫一次码。** 房主的 `RTCPeerConnection` 随页面一起
消失，重连需要一次新的 SDP 交换，而 SDP 交换靠的就是那张二维码 —— 没有信令服务器，
这一步绕不过去。

所以关键在第二半：**重新配对，但认回原来的座位。** `makeMember` 一开始就给每人发了
一枚 `token`（注释里写的就是「断线后凭这个认领原身份」），现在它真的用上了：加入端
把 token 存在本地，下次连接时在 `join` 里捎上，房主据此把这次连接接回**原来那个
成员**，而不是新建一个把旧的晾成幽灵。分数、座位、狼人杀的身份、你画我猜轮到谁，
全部不变。

两条硬约束：

- **token 只发给本人。** 它落在房主本地是为了认座，`snapshot()` 里一个都不许有
  （有回归测试在真序列化过的报文里搜过）。拿别人的 token 想顶掉一个**正在线**的
  座位会被「这座位还有活人」挡回去，只能当新成员；房主自己的座位更是永远不给认。
- **存不下就降级，但不许装作无事发生。** 你画我猜画满时状态能到 MB 级，会顶穿
  `localStorage` 通常 5MB 的配额。这时丢掉进行中的那一局、保住成员和记分牌，并在
  恢复时明说「上一局（你画我猜）画面太大，没能留下来」。

## 还没做

- **自动重连**：掉线的人现在是被「跳过」，回来时得重新扫一次码（虽然能认回原座位）。要让断掉的连接自己接回来，得在没有信令服务器的前提下重新交换一次 SDP —— 那是另一件事
- **移除成员**：房间恢复后可能留下再也不回来了的幽灵成员。删成员会动到每款游戏状态里的成员引用（狼人杀的角色表、棋盘座位），不能顺手做
- 你画我猜还没做的：橡皮擦、填充、按笔画粒度重放（现在只有撤销/全清）

## 待验证的风险

**下面这些全都还没有上真机跑过，别当成已知事实。**

| 风险 | 说明 |
|---|---|
| **两台真机之间的 WebRTC 从未跑过** | 测试里用的是假 `RTCPeerConnection`。它验证了协议、状态机、消息路由，但**验证不了真实 ICE/mDNS/DTLS 能不能通**。这是目前最大的未知 |
| **二维码可能偏密** | 拿一份形状接近真实的数据通道 SDP 量过：SDP 约 1.3KB → deflate 后约 660 字符 → 整条链接约 690 字符 → **v21（101×101）二维码**。满屏显示应当可扫，但没在真机上确认过。内容超出容量时会自动改显示纯文本链接 |
| **Chrome LNA 本地网络访问权限** | Chrome 142 起推行，**Chrome 146 起扩展到 WebRTC**。公网页面访问局域网可能触发权限提示，被拦报 `ERR_BLOCKED_BY_LOCAL_NETWORK_ACCESS_CHECKS`。但 LNA 不适用于 local→local，实际影响待实测 |
| **mDNS host candidate** | 局域网内不配 STUN 也能连通的关键，但组播被禁的网络（部分企业网、开了客户端隔离的热点）会失败 |
| **客户端隔离** | 手机热点与路由器的 AP 隔离会直接掐断点对点连接，需要给用户明确话术 |
| **iOS Safari** | `BroadcastChannel`、`CompressionStream` 的支持情况，以及后台挂起导致连接断开，都待验证。`CompressionStream` 缺失时会自动退回不压缩（码会更大，但功能不受影响） |
